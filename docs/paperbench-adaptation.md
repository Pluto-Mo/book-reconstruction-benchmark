# 从 PaperBench 迁移到整书重构 Benchmark

本文记录 PaperBench 中适合本项目复用的设计，以及不应照搬的部分。它是 V1 的设计依据，不是对 PaperBench 的完整复刻。

## 1. 先澄清 8,316 个叶子节点

PaperBench 的 8,316 个叶子节点是 **20 篇论文各自 Rubric 树的叶子节点总和**，不是每篇论文都有 8,316 个节点，也不是 20 篇论文共同复用同一批内容节点。

它复用的是统一的评分协议：

- 每个样本拥有独立 Rubric 树；
- 叶子节点只判断一个可观察要求；
- 叶子节点由 Judge 做窄范围判断；
- 父节点和根节点由程序确定性汇总；
- 每篇论文先得到一个根分数，再跨论文做宏平均。

每篇论文具体要实现什么、哪些要求更重要、什么证据算通过，仍然是论文专属的。

来源：

- PaperBench 论文：<https://arxiv.org/abs/2504.01848>
- OpenAI Frontier Evals：<https://github.com/openai/frontier-evals/tree/main/project/paperbench>

## 2. 本项目应复用什么

本项目应复用的是“统一协议 + 每书专属义务树”，而不是复制 PaperBench 的代码执行流程。

| PaperBench | 本项目 |
|---|---|
| 一篇论文 | 一本非虚构书 |
| 一篇论文的复现任务 | 一次固定篇幅的整书重构任务 |
| 代码仓库提交物 | `/app/submission.md` |
| 论文专属 Rubric 树 | 书本专属关系与认知原子树 |
| Code / Execution / Result 证据 | 文本证据 / 关系成立 / 反转与缺失检查 |
| 干净容器重新执行代码 | 不需要；只做输出契约和静态文本检查 |
| 每篇论文根分数 | 每本书根分数 |
| 跨论文宏平均 | 跨书宏平均 |

因此本项目的最小评测单位不是“整篇文章好不好”，而是：

> 候选文章是否明确保留了某一个有原书依据、可单独举证的书特异认知义务。

## 3. 共享 Meta-Rubric，书本内容节点不复用

所有书共享顶层维度和裁判协议：

1. 书特异认知结构；
2. 抵抗常识化与空洞化；
3. 有锚点的作者性组织；
4. 硬约束。

每本书独立生成并冻结：

- 核心关系；
- 关系下的认知原子；
- 来源定位；
- `pass_if`；
- `fail_if`；
- 常见假阳性；
- 可接受的同义表达；
- 局部权重及理由。

除字数、文件路径、格式等硬约束外，不应直接复用诸如“是否理解核心思想”“是否有自己的思考”这类通用内容叶子。它们无法说明模型是否真正保留了某一本书独有的认知结构。

## 4. 一本书、书的数量和 Rollout 数量是三个维度

- **一本书的叶子数量**决定单个任务的诊断分辨率；
- **书的数量**决定结论能否推广到不同非虚构作品；
- **每书 Rollout 数量**决定模型成绩对随机性的敏感程度。

大量叶子不能替代多书覆盖；多次 Rollout 也不能把单书案例自动变成通用 Benchmark。

### 30 小时工程验证

V1 的正式目标仍是 5 本书、至少 3 个非虚构领域。为了在有限时间内先验证机制，采用两阶段口径：

1. **开发书 1 本**：用于生成 Rubric、调 Judge、制作扰动样本。它属于 `dev`，不进入对外主分。
2. **保留书至少 2 本**：在冻结公开任务、Schema、Judge Prompt 和权重后运行，作为首轮 `pilot`。
3. 机制通过后扩展到 5 本正式书，再形成 V1 主榜。

单书版本可以称为“一个严谨的 Task”或“Pilot”，但不能据此声称测得了模型的一般非虚构整书理解能力。

## 5. 本项目不需要 Reproduction 阶段

PaperBench 要在第二个干净容器重新运行提交代码，是为了区分“代码写了”与“实验真正执行并产出结果”。

本项目的主要 Artifact 是静态 Markdown，因此流程可压缩为：

```text
Agent Rollout
书稿 Markdown + 固定 instruction
        ↓
/app/submission.md
        ↓
Verifier
硬约束检查 → 证据优先的二元 Judge → 程序汇总
```

需要程序直接检查的内容包括：

- `/app/submission.md` 是否存在且可读；
- 是否为空；
- 字符数是否在冻结区间；
- 是否违反明确格式契约；
- 是否出现大段复制等可程序检测的问题。

这些检查不能替代书特异语义评分。

## 6. Judge 的运行边界

Judge 不重新发明“这本书最重要的是什么”，只执行已经冻结的 Book Card。

每次 Judge 输入应尽量缩小为：

- 当前候选文章；
- 当前一组相关原子；
- 这些原子的来源摘要和定位；
- `pass_if`、`fail_if` 与常见假阳性；
- 固定 Judge Prompt。

默认按同一关系将 3–8 个原子放入一个小批次。关系反转、限定条件删除等高风险原子可以切换为逐原子调用。不要把全书所有标准一次性批量评分，也不要让 Judge 直接输出文章总分。

每个原子的判定顺序固定为：

1. 从候选文章提取最短证据；找不到则记为 `NONE`；
2. 验证引文确实存在于候选文章；
3. 判断证据是否满足当前原子；
4. 独立检查文章是否在其他位置反转或否定该关系；
5. 返回二元结果和可审计理由。

Judge 的置信度只作诊断，不进入质量分。

## 7. 聚合口径

单本书内部：

\[
S_{relation} = \frac{\sum_i w_i s_i}{\sum_i w_i}
\]

\[
S_{book} =
0.7S_{cognitive}
+0.1S_{genericity}
+0.1S_{organization}
+0.1S_{constraints}
\]

其中当前 V1 权重仍是待校准假设。

同一本书多次 Rollout 的主结果使用均值，同时报告标准差。`best-of-k` 只能作为单独诊断指标，不能代替平均表现。

跨书时先得到每本书的归一化根分数，再做宏平均：

\[
S_{benchmark} = \frac{1}{N}\sum_{b=1}^{N}\overline{S_b}
\]

禁止把所有书的叶子直接混在一起平均，否则节点更多的书会获得更高的隐含权重。

## 8. 冻结顺序

正式结果产生前必须依次冻结：

1. 公开任务说明和输出契约；
2. 书稿版本及哈希；
3. Book Card；
4. Judge Prompt、Judge 模型与参数；
5. 聚合权重；
6. Rollout 次数和失败处理；
7. 校准集预期标签。

正式模型结果产生后，不得因为排名“不符合预期”而修改 Rubric。任何修改都必须形成新版本并重新运行全部对比模型。
