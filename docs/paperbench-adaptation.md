# 从 PaperBench 迁移到整书重构 Benchmark

本文记录 PaperBench 中适合本项目复用的设计，以及不应照搬的部分。它是 V1 的设计依据，不是对 PaperBench 的完整复刻。

## 1. 先澄清 8,316 个叶子节点

PaperBench 的 8,316 个叶子节点是 20 篇论文各自 Rubric 树的叶子节点总和，不是每篇论文都有 8,316 个节点，也不是 20 篇论文共同复用同一批内容节点。

它复用的是统一协议：

- 每个样本拥有独立 Rubric；
- 叶子节点只判断一个可观察要求；
- Judge 做窄范围判断；
- 父节点和根节点由程序确定性汇总；
- 每个样本先得到一个根分数，再跨样本宏平均。

每篇论文具体要实现什么、哪些要求更重要、什么证据算通过，仍然是样本专属的。

来源：

- PaperBench 论文：<https://arxiv.org/abs/2504.01848>
- OpenAI Frontier Evals：<https://github.com/openai/frontier-evals/tree/main/project/paperbench>

## 2. 本项目应复用什么

| PaperBench | 本项目 |
|---|---|
| 一篇论文 | 一本非虚构书 |
| 论文复现任务 | 固定篇幅的整书认知重构 |
| 代码与实验 Artifact | `/app/submission.md` |
| 论文专属 Rubric 树 | 书本专属认知结构图 |
| 细粒度可判要求 | 有方向的关系叶子 |
| 父级分层聚合 | 关系覆盖与核心路径完整度 |
| 每篇论文根分数 | 每本书归一化结果 |
| 跨论文宏平均 | 跨书宏平均 |

本项目不直接照搬 PaperBench 的代码复现流程。它借鉴的是：

```text
统一任务与评分协议
+
每个样本独立的隐藏 Rubric
+
窄 Judge
+
确定性聚合
+
校准与冻结纪律
```

## 3. 为什么不能只用“关系 / 原子树”

前一版设计把每本书表示为“8–12 条关系，每条拆成若干二元原子”。这仍可能把作者的思考过程拆成彼此无关的叶子。

整书重构需要进一步保存：

- 节点的论证角色；
- 作者、对手和引用者的立场归属；
- 假设、让步、否定和限定等认识论状态；
- 多条关系共同形成的必需路径；
- 多前提汇合、分支和替代路径；
- 构成性案例在论证中的作用。

因此本项目使用：

```text
Cognitive Structure
├── Nodes
├── Typed Relations
└── Required / Alternative Paths
```

最小评分叶子仍然是窄关系，但关系不能脱离其所属结构和路径。

## 4. 共享 Meta-Rubric，书本内容不复用

所有书共享：

1. 公开 instruction 契约；
2. 认知结构 Schema；
3. Evidence Locator 与 Relation Adjudicator 的职责边界；
4. Judge Prompt 和失败处理；
5. 关系覆盖与路径完整聚合；
6. Harbor 和固定 Agent scaffold；
7. 多次 Rollout 和跨书宏平均规则。

每本书独立生成并冻结：

- 核心问题；
- 认知结构；
- 节点及其角色、立场与状态；
- 有方向关系；
- 必需路径和替代路径；
- 构成性案例；
- 来源定位；
- `pass_if`、`fail_if` 和假阳性；
- 局部权重及理由。

除硬约束外，不复用“是否理解核心思想”“是否有作者感”“是否足够深入”这类通用内容叶子。它们不能证明模型保留了某一本书独有的认知结构。

## 5. 公开任务与隐藏 Rubric

PaperBench 给 Agent 上位任务，详细 Rubric 隐藏在评分端。本项目沿用这一原则：

```text
公开：
重建作者的核心问题、推理路径、条件、反驳和构成性材料

隐藏：
这本书具体有哪些关系、路径、案例、边界、权重和失败模式
```

公开任务过粗会退化成普通摘要；过细会把隐藏答案变成填空题。因此采用“高任务清晰度、低答案泄漏”。

## 6. 一本书、关系数量和 Rollout 数量是三个维度

- 一本书的关系和路径数量决定单任务的诊断分辨率；
- 书的数量决定结论能否推广到不同非虚构作品；
- 每书 Rollout 数量决定成绩对随机性的敏感程度。

大量关系不能替代多书覆盖；多次 Rollout 也不能把单书案例自动变成通用 Benchmark。

### 工程验证

1. 开发书 1 本：生成和修改 Rubric、Oracle、Judge Prompt 与校准变体，不进入对外主分；
2. 冻结协议后，至少 2 本保留书运行正式 Pilot；
3. 机制通过后扩展到 5 本正式书、至少 3 个领域；
4. 每书每模型默认 3 次 Rollout，报告均值和标准差。

关系数量由书的结构决定，不再以固定 25–40 个叶子为硬目标。

## 7. 本项目不需要代码 Reproduction 阶段

PaperBench 需要把代码提交物复制到干净容器重新执行。本项目的主要 Artifact 是静态 Markdown，因此流程是：

```text
Agent Rollout
书稿 Markdown + 固定 instruction
        ↓
/app/submission.md
        ↓
Verifier
├── 硬约束
├── Evidence Locator
├── Relation Adjudicator
├── Quote Validator
└── Graph Aggregator
```

程序直接检查：

- 提交文件是否存在且可读；
- 是否为空；
- 字符数是否在冻结区间；
- 是否违反格式契约；
- 是否存在可程序检测的大段复制。

这些检查不能替代书特异语义评分。

## 8. Judge 的运行边界

Judge 不重新发明“这本书最重要的是什么”，只执行冻结 Book Card。

运行时分开：

1. Locator 找候选文章引文，不给分；
2. Adjudicator 根据关系、候选引文和必要上下文判断；
3. Quote Validator 验证引文；
4. 程序聚合。

Judge 可以连接候选文章已经明确表达的分散关系，但不能用原书知识补入候选文章缺失的实质性桥接命题。

关系可以小批次执行，但高风险条件、否定、关系反转、立场归属和构成性案例优先逐关系判断。

## 9. 聚合口径

### 9.1 关系覆盖

\[
C_S = \frac{\sum_r w_r y_r}{\sum_r w_r}
\]

### 9.2 路径完整

- `mandatory` 路径全部关系通过才完整；
- 同一 `alternative_group` 至少一条完整路径通过；
- 一个结构所有必需路径和替代组满足后，`path_complete = 1`。

Pilot 同时报告：

```json
{
  "cognitive_relation_coverage": 0.68,
  "complete_core_path_rate": 0.31
}
```

不要只使用“全部通过 / 全部失败”，否则缺一条关系和全部缺失无法区分；也不要只用叶子加权平均，否则零散命中会冒充完整路径。

最终单一 `reward` 在开发书与校准样本试跑后再冻结。Harbor 兼容阶段可暂用关系覆盖作为 `reward`，但必须保存路径完整率。

## 10. 最终结论不重复计分

若结构是：

```text
H → E → M → C → T
```

`T` 是路径终点，不在路径外再获得一份高权重奖励。

“只写 T”的受控变体必须显著低于完整路径。如果所有模型都能写出 T，它只承担基本有效性检查，不承担主要区分度。

## 11. 多次 Rollout 与跨书汇总

同一本书多次 Rollout：

- 主结果使用均值；
- 同时报告标准差；
- `best-of-k` 只作诊断；
- 超时、缺失提交和 Verifier 失败规则提前冻结。

跨书先得到每本书归一化结果，再宏平均。禁止把所有书的关系叶子直接池化。

## 12. 冻结顺序

正式结果产生前依次冻结：

1. 公开任务说明和输出契约；
2. 书稿版本及哈希；
3. 认知结构 Schema；
4. Book Card；
5. Oracle 满分可达性；
6. Locator / Judge Prompt、模型与参数；
7. 聚合规则；
8. Rollout 次数和失败处理；
9. 校准集预期标签；
10. Harbor 与 Agent scaffold 配置。

正式模型结果产生后，不得因为排名不符合预期而修改 Rubric。任何修改必须形成新版本并重新运行全部对比模型。
